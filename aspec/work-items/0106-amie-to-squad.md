# Work Item: Enhancement

Title: amie to squad

Issue: issuelink

## Summary:
- This work item transitions `amie` to being called `squad` and bundles a variety of fixes/enhancements:

1) The rename:

1a) All code, docs, text, UX, etc. should be transitioned from `amie` to `squad` with `awman squad` and `~/.awman/squad/` being the roots for CLI and filesystem, respectively. This is an unreleased feature so there is NO migration, just a straight rename everywhere in the repo.

1b) Conditions are now called `Tasks` and should be similarly renamed/replaced everywhere including filepaths, db schemas, docs, code, etc.

2) The Task creation experience:

2a) When creating a Task, the user should be given a large freeform textbox when creating the task description instead of the current 1-line box (just like 'new spec --interview'). The title of that modal should also be generalized to 'Describe the new squad task including its triggering conditions and how squad should handle the task each time it is triggered'

2b) Each task should BY DEFAULT run bound to a task-specific and durable ~/.awman/squad/tasks/{name}/workspace directory. The user may CHOOSE to bind the task to a different folder on the machine, but allow them to choose between 'Default Task Workspace' or 'Custom Folder / Repo' before forcing them to enter a folder path. If the path the user enters for the custom option is NOT a git root, simply warn them and ask if they would like to keep or change their choice.

2c) The user should be able to add overlays to a task when creating it, so that squad agents/workflows can access things like SSH keys, env vars, directories, etc. — the same overlay mechanism (`dir()`, `ssh()`, `env()`, `skill()`) already available to `--overlay` flags and workflow steps.

3) The agent execution / attach experience

3a) When the daemon executes agents, their stdout/stderr should not be output into the daemon's own logs, but instead redirected to a `~/.awman/squad/tasks/{name}/runs/{run-id}/{container-name}.log` file unique to each container within each run of each task.

3b) The daemon's own logs SHOULD be rich and informative about the entire lifecycle and all actions taken with request to squads including all actions taken by the administrator/user and all scheduler/agent lifecycle events, just no live agent stdout/stderr. Include a periodic update any time any agent containers are running that prints a list of running agents/containers, which task they're associated with, how long they've been running, etc. Don't print the summary if nothing is running

3c) Whenever the user attaches to a running task/workflow, the container window should show the actual running agent (i.e. the TUI of the actual agent, running in interactive/PTY mode), not just drop them into a shell within the agent container as it does today. All agents should be run in interactive/PTY mode even if the user does not attach to them.

4) Error message: "Load failed: 5: Input/output error Try running 'launchctl bootstrap' as root for richer errors" is output in the TUI any time the keyboard shortcut for opening the special tab from the new-tab dialog is pressed and the daemon is not already running

5) UX: The squad TUI UX should be a grid of 'task cards' (i.e. ratatui rounded rectangles with title/summary/last/next) rather than the current spreadsheet-like table. Give the rectangles generous size and spacing to make it feel modern. Also, the detail modal that appears when pressing enter on a card should also have a tooltip with the other actions (attach, pause, etc) for that specific task.

6) Task workspace durability and worktree correctness:

6a) A task's durable task directory (`~/.awman/squad/tasks/<name>/workspace/`) must never be deleted, emptied, or replaced between runs — it stays intact for the full lifetime of the task, only removed when the task itself is deleted.

6b) When a task uses its durable task directory as its workspace, a git worktree must not be used (and generally can't be, since the directory isn't a git repo) — the workspace is mounted directly.

6c) When a task uses a custom directory that IS a git repo, a worktree must always be used for that task's runs, and the daemon's log must record where that worktree lives and what happened to it (kept/merged/discarded) when the workflow ends.

6d) The leader must have a reliable, per-run way to signal whether the task's condition was met — a leftover `workflow.toml` from a previous run is not sufficient evidence on its own, since the leader may legitimately choose to reuse or recreate that file across runs.

6e) When a task uses a custom directory, its runs must still get the durable task workspace mounted as a context overlay (the same mechanism `context(workflow)` uses), so task-scoped persistent data survives across runs regardless of which workspace mode was chosen.

6f) Change the default evaluation interval for newly created tasks from `5m` to `6h`.

## User Stories

### User Story 1:
As a: user

I want to:
define a squad task in one freeform description — what to watch for, what to do about it, and what host resources (SSH keys, env vars, directories) it needs — and have it default to its own durable workspace without me having to think about mount scope

So I can:
get a routine "when X happens, do Y" automation running quickly, with the same guardrails and resource-access model I already use for manual `exec workflow`/`chat` overlays

### User Story 2:
As a: user

I want to:
see my squad tasks as a glanceable grid of cards instead of a cramped table, and attach straight into the actual agent TUI running a task — not a bare shell — whether it's mid-evaluation or mid-workflow

So I can:
quickly assess what's running and dive into a live, faithful view of an in-progress task the same way I'd watch any other agent session

### User Story 3:
As a: operator/admin

I want to:
read the daemon's own log and get a clear, chronological account of every scheduler tick, task lifecycle event, and admin action — with a live "what's running right now" summary — without it being drowned out by raw agent stdout/stderr

So I can:
diagnose daemon-level problems quickly, while still being able to go find any individual container's full output in its own per-run log file when I need it

### Part 2 — Task creation UX (2a, 2b, 2c)

**2a — Freeform description textbox.** The interview flow (`collect_condition_interview` in `src/command/commands/squad/commands.rs`, invoked from both `awman squad add --interview` and the TUI's `n` key via `SquadCommandFrontend::ask_condition_description`/`ask_task_description`) currently collects the description through whatever single-line `Dialog::TextInput` the TUI's interview driver uses for that field. Switch that one field to `Dialog::MultilineInput` (already defined in `src/frontend/tui/dialogs/mod.rs` and used by `new spec --interview` — reuse it verbatim, do not invent a second multiline widget). Retitle it to: *"Describe the new squad task including its triggering conditions and how squad should handle the task each time it is triggered"*. The CLI `--interview` path (no TTY dialog, plain stdin prompt) should use the equivalent multi-line stdin read the `new spec --interview` CLI path already uses, for parity. `--description <text>` (non-interview, scripted) is untouched — it already takes a full string.

**2b — Default vs. custom task workspace.** Add a workspace-choice step to the interview, after the description and before mount scope:
- Prompt: *"Task Workspace"* with two choices — **"Default Task Workspace"** (bind the task to a fresh, durable `~/.awman/squad/tasks/<name>/workspace/` directory, created by `SquadPaths`/`TaskLauncher` seeding, analogous to the existing condition-dir seeding in `src/engine/squad/launcher.rs`) or **"Custom Folder / Repo"** (prompts for a path).
- If **Custom Folder / Repo** is chosen: collect a path, then check whether it is a git root (reuse whatever git-root detection `Session::open_at_git_root`/`git_root_of` already does elsewhere — do not write a second one). If it is not a git root, warn ("this path is not the root of a Git repository") and ask **keep this path** / **choose a different path**, looping back to the path prompt on the latter. This mirrors the existing `mount_scope` capture-once-at-creation semantics: whichever path is chosen becomes the task's mount root and is never widened later, same as the existing `repo_scope`/`mount_scope` fields.
- Data model: `Task` (formerly `Condition`) needs its `repo_scope` field's meaning generalized — today `repo_scope` is implicitly "the repo you were in when you ran `add`"; this makes explicit that a task's `repo_scope` may be the default per-task workspace directory (which is *not* itself a git repo — it's a plain durable directory) rather than an existing git repo. Confirm `mount_scope: cwd|gitroot` still makes sense for the default-workspace case (likely: default-workspace tasks always mount the whole workspace dir, since there's no git root to distinguish `cwd` from `gitroot`) and adjust `MountScope`/its resolution in `src/engine/squad/launcher.rs`/`resolve_agent_options` accordingly. Document the resulting semantics precisely in code comments on `Task`, since this is a real behavior change layered onto the rename.
- CLI equivalent: extend `awman squad add` with `--workspace <default|path>` (default: `default`) so scripted creation has parity with the interview.

**Durability and worktree behavior for the two workspace choices** (this is a real behavior change, not just a rename, and is the load-bearing part of 2b):

- **Default Task Workspace is truly durable across runs.** `~/.awman/squad/tasks/<name>/workspace/` must never be deleted, emptied, or replaced between runs of the same task — only deleting the task itself (`awman squad remove`, with the existing "also delete its persistent directory?" prompt) may remove it. This directly conflicts with today's `seed_condition_dir`/`seed_task_dir` (`src/engine/squad/launcher.rs`), which currently does `std::fs::remove_file(dir.join("workflow.toml"))` before every run specifically to clear a stale generated workflow. That deletion must be removed for the durable-workspace case — see the `workflow.toml`-is-not-a-reliable-signal point below for why the evaluator can no longer depend on clearing it. Re-seeding the reference assets (`example-workflow.toml`, usage docs) idempotently on every run is fine to keep (they're static, reference-only files, not task state); deleting or truncating anything the leader/workflow may have written is not.
- **Default Task Workspace never uses a git worktree — one is neither needed nor possible.** The durable workspace directory is a plain filesystem directory, not a git repository (unless the leader/workflow itself chooses to `git init` something inside it, which is out of scope here and not this work item's concern). The existing forced-worktree-isolation guardrail (`docs/16-amie.md`'s "Worktree isolation is always forced on" / the `--worktree` equivalent in `ExecWorkflowCommand`) assumes a git root to branch a worktree from and must be skipped entirely for a default-workspace task — mount the workspace directory directly, the same way a non-git `cwd` session already works elsewhere in awman (`Session::open_at_git_root`'s non-git fallback, already reused for the amie/squad tab's synthetic session in WI 0102). Audit `ExecWorkflowCommand`'s worktree setup/teardown path (`worktree_lifecycle.rs` and its call sites) for an existing "no git root, skip worktree" branch to reuse rather than adding a parallel one.
- **Custom Folder / Repo that IS a git root always uses a worktree — no exception.** This preserves the existing safety property (two runs of the same or different tasks touching the same repo don't step on each other's working tree) for the one workspace choice where it's actually possible. The daemon's lifecycle log (Part 3b) must record, for every such run, the worktree path created and its disposition when the workflow ends (kept with its branch name, merged, or discarded) — this is exactly the existing `report_worktree_created`/`report_worktree_kept`/`report_worktree_discarded`/`report_merge_conflict` callbacks on `WorktreeLifecycleFrontend` (`src/frontend/squad/unattended.rs`), which already log at `info`/`warn` — confirm they fire for every custom-directory run and are not accidentally skipped for squad specifically.
- Because "Custom Folder / Repo that is *not* a git root" is also possible (2b's existing warn/keep-or-change flow doesn't forbid proceeding, it only warns), that case behaves like the default workspace: no worktree, direct mount, and the same durability expectation — the user picked a specific folder precisely because they want that folder used and preserved, so treat it as no less durable than the default workspace. Update `MountScope`/its resolution so worktree-usage is derived from "is the effective task root a git repo," not from `cwd` vs `gitroot` alone.

**A reliable per-run signal for whether the task's triggering condition was met.** Today's `EvaluationOutcome` is decided by `generated_path.exists()` (`workflow.toml` in the task directory) immediately after the leader agent's run (`src/command/commands/squad/evaluation.rs`, formerly `amie/evaluation.rs`) — this only works because `seed_condition_dir` deletes any prior `workflow.toml` before every run. Once the durable workspace is no longer cleared between runs (above), a leftover `workflow.toml` from three runs ago would cause every subsequent evaluation to be misread as "triggered," even when the leader wrote nothing new this run. Fix: give the leader an explicit, run-scoped way to signal its verdict, independent of whether `workflow.toml` happens to already exist on disk:
  - Add a small structured marker the leader writes fresh every run to indicate its verdict for *this* run — e.g. a `verdict.json`/`.squad-verdict` file written into the run-scoped log/metadata directory from Part 3a (`runs/<run-id>/`), not into the durable workspace root, so it can never be confused with the leader's own durable outputs and never needs "staleness" cleanup itself (a new file per run, in a new per-run directory, is inherently unstale). Minimal shape: `{"triggered": bool}`, optionally with a short reason string for the daemon log.
  - Update the leader prompt (`build_amie_leader_prompt`/its squad-renamed successor, and `src/assets/dynamic/squad-leader-prompt.md`) to instruct the leader to always write this verdict file, in addition to (optionally) writing/reusing `workflow.toml` in the durable workspace when triggered. Be explicit in the prompt that the leader **may reuse an existing `workflow.toml` from a previous run or write a new one** — both are valid when triggered — but the verdict file is mandatory and authoritative regardless of which it chose.
  - `evaluation.rs`'s post-run check becomes: read the verdict file; if absent or unparseable, treat as `Failed` (an evaluation that didn't follow protocol is an error, not a silent "not triggered") rather than falling back to the old existence-based guess. If `triggered: false`, return `NotTriggered` even if `workflow.toml` exists on disk (e.g. from a previous triggered run) — its mere presence is no longer sufficient, matching the summary's explicit callout. If `triggered: true`, proceed to validate whichever `workflow.toml` is now on disk (freshly written or reused) exactly as today's `validate_generated_workflow` already does.
  - This changes `WorkflowRepairLoop`'s repair trigger too: today "first attempt + file missing" means not-triggered; that special case should become "first attempt + verdict says not triggered" (or "no verdict file" as noted above), and a repair attempt's validation failure path is otherwise unchanged.

**2c — Overlays at task creation.** Add an `overlays: Vec<String>` field to `Task`/`CreateTask`, storing raw overlay-spec strings in the same syntax already accepted by `--overlay` (`dir()`, `ssh()`, `env()`, `skill()` — parsed by `parse_overlay_list` in `src/command/commands/mod.rs`/wherever it's currently defined, referenced today from `chat.rs`'s `ChatFlags::overlay`). Validate every entry with `parse_overlay_list` at creation time (`awman squad add`/interview) so a malformed overlay spec is rejected before the task is ever persisted, not discovered at first run.
- Persist as a new column in `squad_tasks` (e.g. a JSON- or newline-encoded `TEXT` column, consistent with how other list-shaped fields are stored in `condition_store.rs`/`task_store.rs` today — check whether any existing field already needs this pattern and reuse it rather than inventing a new encoding).
- At run time, `SquadAgentLauncher::run_leader` (formerly `AmieAgentLauncher`) must merge the task's stored overlays into `AgentRunOptions.directory_overlays`/the overlay-resolution path the same way `collect_all_overlay_specs` merges global config, repo config, `AWMAN_OVERLAYS`, and CLI flags today (see `src/engine/overlay/mod.rs`, `src/engine/agent/mod.rs`). Task overlays are additive with global/repo overlays, consistent with the existing "all overlay sources combine" rule in `docs/08-overlays.md` — do not make them exclusive.
- Interview UX: after the workspace-choice step, offer an optional multi-entry prompt ("Add an overlay? [dir()/ssh()/env()/skill() syntax, blank to finish]"), looping until the user submits blank. CLI: repeated `--overlay <spec>` flags, exactly like `chat`/`exec workflow` already accept, feeding the same `overlays: Vec<String>` field.
- `awman squad show <name>` / the TUI detail modal should list the task's configured overlays alongside description, mount scope, interval, etc.
- **Custom-directory tasks still get the durable task workspace, as a context overlay.** When the user chooses "Custom Folder / Repo" (2b), the task's leader/workflow containers mount the custom folder as the primary working tree, but must *also* get `~/.awman/squad/tasks/<name>/workspace/` mounted in — exactly as if `context(workflow)` had been requested — so the task always has one durable, task-scoped location for persistent files/data regardless of which workspace mode was chosen, for the task's full lifetime. Concretely: still create/seed the default workspace directory even for a custom-directory task (it's needed either way), and add it to the run's context overlays via whatever mechanism `context(workflow)`/`context(global)` already uses for context-directory mounting (`src/data/fs/context_dirs.rs`, referenced from `AgentRunOptions.context_overlays` — see `run.context_overlays` usage in `src/engine/agent/mod.rs`), not the general-purpose `dir()` overlay syntax, since this is an always-on structural mount rather than a user-specified overlay. Confirm the mount path inside the container is stable and documented (e.g. the same convention `context(workflow)` already uses) so a task's agent can reliably find it run over run.

### Part 2.5 — Default evaluation interval (6)

Change the default `--interval` for `awman squad add` (interview and scripted) from `5m` to `6h`. This is a one-line default-value change at `FlagSpec { long: "interval", ..., default: FlagDefault::Str("5m"), ... }` in `src/command/dispatch/catalogue.rs` (~line 1110) — update the literal to `"6h"` and update the flag's `help` text example accordingly. ### Part 3 — Execution, logging, and attach (3a, 3b, 3c)

**3a — Per-container run logs.** Today `UnattendedFrontend::take_io()` (in `src/frontend/amie/unattended.rs` → `src/frontend/squad/unattended.rs`) drains stdout/stderr through `spawn_log_drain`, which writes every line to `tracing::info!` — this is what currently puts raw agent output into the daemon's own log file. Replace this: each run gets a `run-id` (there is already a `RunId` type in the data store — reuse it, do not invent a second id scheme) and, for each container launched under that run, open a file at `~/.awman/squad/tasks/<name>/runs/<run-id>/<container-name>.log` (create the `runs/<run-id>/` directory before the container starts) and drain stdout/stderr bytes into it instead of into `tracing`. Both streams can share one file (interleaved, as a terminal would show them) since 3c also puts these agents into PTY mode, where stdout/stderr are typically already merged at the PTY layer — confirm this against how `spawn_pty_bridged_docker` (`src/engine/container/docker.rs`) exposes the two streams and adjust (separate files only if the PTY bridge genuinely keeps them distinct).
- The per-run log directory is a natural place to also drop minimal run metadata (start time, agent, model, exit code) if useful for `awman squad show`, but keep this an additive nice-to-have, not a requirement — the summary above is about output redirection, not a new metadata format.
- `awman squad logs` (daemon log tail) is unaffected — it keeps tailing the daemon's own log file, which after this change contains lifecycle events only (3b), not agent output. Consider whether a new `awman squad logs <name> [--run <run-id>]` (or reusing `attach`'s discovery) is warranted to let a user tail a finished run's per-container log — evaluate against the existing "no SSE/streaming, ordinary polled request/response" architecture note in `aspec/work-items/0102-amie-frontends.md`; a local `tail -f`-style read of the log file (like the existing `run_logs` daemon-log tail) is consistent with that, a new streaming API route is not.

**3b — Rich daemon lifecycle logs, with a periodic running-agents summary.** With 3a removing raw agent output from the daemon log, audit `src/engine/squad/scheduler.rs`, `src/command/commands/squad/daemon.rs`, and `src/frontend/squad/unattended.rs` for what lifecycle/admin events are already logged via `tracing::info!`/`warn!`/`debug!` (tick start/count, due-condition selection, concurrency-cap deferral, workflow-state-path recording, worktree created/kept/discarded, workflow step status, workflow completed, CRUD calls arriving at the gateway) and make sure every administrator/API action (add/remove/pause/resume/start/stop, key mint/refresh) and every scheduler/agent lifecycle transition (task selected for evaluation, evaluation container launched, evaluation decided act/no-act, workflow generated, each step launched/finished, task backed off, task run finished with outcome) is logged at `info` level with enough structured fields (task name, run id, container name) to reconstruct a timeline. Promote any of these currently at `debug` that belong at `info` for this purpose.
- Add a periodic "running agents" summary: on each scheduler tick (or a lighter-weight timer alongside it — do not couple this to the 30s `TICK_INTERVAL` if a shorter cadence reads better, but avoid adding a second independent polling loop if the tick loop already fires often enough), if one or more squad containers are currently running, log one structured line/block per running container: task name, container name, agent/model, and elapsed running time (derived from the container's recorded start time — the scheduler/store already has `started_at` on `Run`). **Emit nothing when nothing is running** — this must not turn into a heartbeat spamming the log every tick.

**3c — Interactive/PTY execution and faithful attach.** Two related changes:
1. **All squad-launched agents run in PTY mode**, not piped, regardless of whether anyone is attached. In `UnattendedFrontend::take_io()`, set `resize`/`initial_size` to `Some` (a reasonable fixed default size, e.g. 120×40, since there's no real terminal to size against) instead of `None`, so `AgentRuntimeEngine::build`/`run_with_frontend` takes the PTY path (`spawn_pty_bridged_docker` in `src/engine/container/docker.rs`) instead of the piped path. This is what makes the running agent an actual interactive TUI process inside the container rather than a plain piped stdout stream, and it's a prerequisite for attach in item 2 to show something meaningful. Verify this doesn't change agent behavior for agents that behave differently under a TTY vs. piped stdout (most CLI agent tools do — that's the point) and that the stuck/grace timeout logic in `src/engine/container/timing.rs` still functions correctly against PTY output.
2. **Attach shows the real agent, not a shell.** Confirm (this may already be true per WI 0102's Part 3, which built `attach` on top of `AgentRuntimeEngine::attach` → `run_with_frontend`, the same primitive real interactive sessions use) that today's attach path execs into the *agent process* rather than opening `docker exec -it <container> sh`. If the current implementation is in fact dropping users into a shell (per this work item's summary, it apparently is), find where — likely `docker.rs`'s `attach()` (~line 373) building a `docker exec` command — and fix it to attach to the PID-1 agent process's PTY (matching whatever `run_with_frontend`'s normal launch path already does for a freshly-started interactive session) instead of spawning a new shell process in the container. This should converge with 3c(1): once every agent already runs attached to a PTY from launch, "attach" should mean "connect a new client to that existing PTY" (or re-exec into the same running agent process), never "start a new shell alongside it."

### Part 4 — Fix the spurious "Load failed" error (4)

The reported string ("Load failed: 5: Input/output error Try running 'launchctl bootstrap' as root for richer errors") is a raw macOS `launchd`/POSIX I/O error, not text this codebase emits anywhere (confirmed: no match for "Load failed" or "launchctl bootstrap" in `src/`). It's surfacing because `App::build_amie_tab`/`build_squad_tab` (`src/frontend/tui/app.rs`) propagates `ensure_running()`'s error via `.map_err(|e| e.to_string())` and `open_or_focus_amie_tab`/`open_or_focus_squad_tab` puts that string verbatim into the status bar — so whatever platform-level failure occurs while `SquadSupervisor::ensure_running()` tries to spawn/detach the daemon process on first `Ctrl-A` is leaking its raw OS error text straight to the user instead of being wrapped.
- Trace `SquadSupervisor::ensure_running()` → `spawn_detached()` (`src/data/fs/daemon_process.rs`) on macOS: this is almost certainly where a `posix_spawn`/`launchd`-related I/O error originates when the daemon binary can't be spawned detached (e.g. sandboxing/permissions on the daemon binary path, or the detach mechanism itself invoking something launchd-adjacent).
- Fix at the source: `daemon_process.rs`'s spawn path should catch the underlying OS error and wrap it in a clear `CommandError`/`EngineError` describing *what awman was trying to do* ("failed to start the squad daemon: <cause>") rather than letting an opaque platform error string bubble all the way to the TUI status bar unwrapped. This is a general robustness fix to daemon spawning, not squad-specific, so also check whether `awman api start`'s spawn path (which likely shares `daemon_process.rs`) has the same leak.
- Regardless of the root platform cause, `build_squad_tab`/`open_or_focus_squad_tab` should never show a bare OS error string in the status bar — at minimum wrap unrecognized errors with a prefix like "failed to start the squad daemon: " so raw platform errors are at least attributable, even if this work item can't reproduce/fix every possible underlying `launchd` failure mode on every macOS configuration.

## Edge Case Considerations:

- **Task creation is interrupted mid-interview** (Ctrl-C, dialog dismissed): no partial `Task` should ever be persisted — `collect_condition_interview`/`collect_task_interview` must not call the store until every field, including the new workspace-choice and overlay steps, has been answered, matching the existing all-or-nothing behavior.
- **Custom workspace path does not exist at all** (vs. exists-but-not-a-git-root): distinguish "not a git root" (warn + keep/change) from "path does not exist" (hard error, since there is nothing to mount) — do not silently `mkdir` an arbitrary user-entered path the way the default workspace path is created.
- **Custom workspace path is a git root but is also a parent directory of the current repo, or otherwise conflicts with the "never mount a parent directory" security constraint** (`CLAUDE.md`/`aspec/architecture/security.md`): apply the same parent-directory confirmation prompt other awman mount-scope flows already use; do not let squad's custom-folder path bypass that check just because it's a new entry point.
- **Overlay spec is syntactically valid but references a nonexistent host path/env var**: per `docs/08-overlays.md`, a missing `dir()` host path is a hard error *at launch time*, while a missing `env()` var is silently absent — task creation only validates *syntax* (via `parse_overlay_list`), not host-side existence, since the host state at creation time may differ from host state at each future run. Don't over-validate at creation.
- **A task's overlays collide with global/repo overlays mounting the same container path**: follow whatever existing collision behavior `collect_all_overlay_specs`/`OverlayEngine` already has for combining multiple overlay sources (error vs. last-wins vs. first-wins) — do not invent new collision semantics for task-level overlays specifically.
- **Renaming `awman.amie.condition` → `awman.squad.task` container label**: since there is no migration, any container launched by a pre-rename build simply won't match `list_running_with_name_prefix`/`awman-squad-` discovery after the rename — acceptable given "no migration," but worth a one-line note in the daemon's startup log if it finds stray `awman-amie-*` containers, so a developer mid-rebuild isn't confused by orphans (not required to auto-clean them).
- **Per-run log directory creation races with container startup**: `runs/<run-id>/` must exist before the container's stdout/stderr bridging task starts writing to it — create the directory synchronously before launch, not lazily on first byte.
- **Daemon crashes mid-run**: the per-container log file up to the crash point must remain readable (flush/no buffering that loses the tail on an unclean daemon exit) — use line-buffered or unbuffered file writes for these logs, consistent with why `tracing`-to-file already behaves this way for the daemon log.
- **The periodic running-agents summary during a tick where every previously-running container just exited**: must correctly emit *nothing* that tick (per the explicit "don't print if nothing is running" requirement), not a stale summary from the prior tick's snapshot.
- **PTY-mode agents and non-interactive agent CLIs**: some configured agents may not behave sensibly when given a PTY with no real terminal attached (e.g. an agent that queries terminal size and misbehaves on an unusual/default one) — confirm the fixed default PTY size chosen for unattended runs doesn't break any currently-supported agent, or make it configurable if one does.
- **Attach while the daemon has crashed mid-workflow**: unaffected by this rework — 3a/3c only change *where* output is captured and *how* the agent process runs, not the "attach is a direct runtime connection, independent of the daemon" guarantee already established in WI 0102; preserve that property exactly.
- **Grid reflow mid-attach or mid-modal**: resizing the terminal while the card grid is showing must not lose the current selection (map the previously-selected task by identity, not by grid position, across a reflow) or corrupt an open detail modal's target task.
- **A task grid with zero tasks**: render an empty-state message in place of the grid rather than a zero-card layout with dangling borders.
- **A default-workspace task's leader crashes or is killed mid-write**: whatever partial files it left in the durable workspace must survive to the next run untouched (no re-seeding wipes them) — only the reference/example assets are safe to rewrite idempotently; never re-run any logic that deletes user/leader-written content on the next tick's seed step.
- **A default-workspace task run writes no verdict file at all** (leader ignored the protocol, crashed before writing it, or the container was killed): treat as `Failed`, not `NotTriggered` — a missing verdict is a broken run, not evidence of a legitimately-unmet condition, and should back off/alert like any other evaluation failure rather than going silent forever.
- **A custom-directory task's git root is deleted or moved on disk between runs**: the worktree-creation step must fail loudly (existing `PreWorktreeDecision`/worktree-lifecycle error paths) rather than silently falling back to no-worktree/direct-mount — a task that was explicitly configured against a git repo must not quietly start operating directly on a path that turns out not to be one anymore.
- **A custom-directory task's repo is a git root at creation time but the user later reinitializes it, changes its remote, or it becomes a non-git directory**: mount-scope/worktree behavior is captured once at creation (existing convention) and is not re-derived per run — document this explicitly so "always uses a worktree" is understood as "as evaluated at creation," consistent with `mount_scope`'s existing capture-once semantics.
- **The context overlay mounting the durable workspace into a custom-directory task's containers collides with a path the custom directory (or another overlay) already uses inside the container**: apply the same "no silent overwrite of a live mount" guard `OverlayEngine`/`context_dirs.rs` presumably already enforces elsewhere for `context(workflow)`/`context(global)` collisions — do not special-case squad here.
- **Changing the default `--interval` to `6h` retroactively**: this only affects *new* tasks created after the change (the flag default), never any already-created task's stored `interval_secs` — confirm no code path re-derives an "unset" interval from the current default at read time rather than from what was persisted at creation.
